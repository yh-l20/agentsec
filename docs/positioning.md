# 为什么做元星木

2026-09-12。元星木先服务这样的人：已经有自己的模型接口，想让 AI 整理报价、预算或工作资料，又希望自己决定交给它哪些文件、什么时候结束使用。日常入口是本机网页工作台，回答仍在 OpenClaw 原来的聊天界面里。当前需要 Ubuntu / WSL，首次安装仍有环境要求。

2–4 人团队先把这件具体的事做好：普通用户能装起来，放入自己的资料，完成一次有用的工作，下次还能继续。开源核心和开发接入服务于这个使用过程。仓库增长来自别人实际使用、复用和贡献；当前没有万星、付费客户或独立持续使用的证据。

## 把哪件事做大

用户应该能说清楚：“这项工作允许读取哪些资料，资料是否交给云端模型，什么时候不再允许继续读取。”后续接入外部发送时，还要明确结果可以交给谁。模型受到网页、邮件或工具返回内容影响后，权限也应继续由程序执行检查。

当前工作台已有一条可使用的流程：

- 连接自己的模型接口，选择允许读取的短文本，为每项工作保存独立的资料和权限。
- 打开 OpenClaw 原生聊天，让模型阅读资料、整理内容，在聊天中查看并核对结果。
- 暂时关闭工作；正常关闭且权限未被收回时，重新打开原来的资料、聊天和权限。
- 永久收回资料权限，拒绝后续通过元星木读取和发送资料。

所选模型会收到聊天和使用的资料；云端模型也一样。收回权限不能清除模型已经读过的内容，也不能撤回已完成的发送。关闭终端或浏览器不会停止已经运行的 AI，要先在工作台点击“暂时关闭”。

目前工作台支持 OpenClaw 2026.9.4，最多导入 8 份 UTF-8 文本，每份 256 KiB、合计 1 MiB。它没有邮件、飞书或 Slack 的现成连接器。“起草邮件，由本人确认后发送”是可能的下一步，本版尚未实现这套完整流程，不能列为已有功能。Hermes 的终端接入验证也不等于工作台提供了 Hermes 聊天界面。

底层已有持久权限库、固定资源与接收位置的执行服务、Linux 隔离和真实接收端验收。旧发送演示保留了内部送达、外部未送达的结果；新工作台上手视频演示的是连接模型、导入资料、整理预算、关闭重开和收回权限，没有配置额外发送位置。这两份记录各自说明自己的验证范围。

安装器预览已独立发布为 [`installer-0.1.0a1`](https://github.com/yh-l20/agentsec/releases/tag/installer-0.1.0a1)，固定安装现有元星木 `0.4.0a1`、Node.js `24.16.0` 和 OpenClaw `2026.9.4`。它减少手工安装步骤，仍需 Ubuntu 24.04 / WSL Ubuntu 24.04 x86_64、系统 Python、至少 2 GB 空间和网络连接；WSL 本身由用户准备。Ubuntu 与 WSL 均完成实际启动、原生 OpenClaw 网页、关闭重开、撤权与停止验收；这不是模型攻击评测。官网提供安装器下载，原手工入口继续保留。

## 为什么与模型能力增长相关

模型更强，可能减少无意工具错误，也可能更善于组合动作、尝试替代出口和隐藏意图。两者同时成立。把权限核对放在模型之外，可以让授权决定不依赖模型愿意遵守规则，但仍须持续检查是否漏了执行通道。

“内容安全完全与能力无关”也过于绝对：自动化传播、个性化操控和规模化欺诈会随能力变化。这里选择任务执行权限，是因为后果、权限和拦截位置更容易明确验证，而不是因为其他安全问题都没有价值。

真正需要研究的是：攻击者模型能力和尝试预算增加时，在同样正常业务要求下，仍能找到多少越权路径；防御为保住边界又牺牲了多少正常完成率。固定脚本演示只证明已测机制，不证明抵抗更强模型的能力曲线。

## 与同类安全方案的架构对照

以 [FIND-Lab/AgentWard](https://github.com/FIND-Lab/AgentWard/tree/46309333bdfdbcf4701000c1dad85b33b4a0e7ef)（包版本 2026.5.9）为参考对象，区分应用层插件防护与系统级执行隔离的边界差异：

| 关注维度 | 应用层插件式防护（如 AgentWard） | 元星木执行边界架构 |
| --- | --- | --- |
| 防护生效层级 | 依托框架提供的生命周期钩子，主要在应用层进行规则与模型裁判。 | 宿主级独立 Broker 核对实际调用，Linux 命名空间/bubblewrap 约束底层网络与文件系统。 |
| 交互与审批方式 | 原生插件提供配置命令、告警信息与会话级干预。 | 提供独立宿主工作台，支持任务级资料范围预选、进程级权限持久收回与断点重开。 |
| 凭据与权限隔离 | 保护逻辑运行在 Agent 进程内部或紧密依附于其框架运行时。 | 敏感凭据留在宿主环境，Worker 进程无权访问底层授权库与真实外发出口。 |
| 状态持久性与子任务继承 | 多作用于当前会话或特定请求上下文。 | 读取标签由可信宿主的 SQLite 账本按任务家族持久保存，Worker 无权清空；子任务的资源和目的地权限不得超过父任务。 |
| 防护目标定位 | 侧重对输入输出内容、越狱提示与敏感词的语义审计。 | 侧重对实际外部动作、数据外发管道和执行载荷的强行授权约束。 |

源码入口参考：[插件钩子](https://github.com/FIND-Lab/AgentWard/blob/46309333bdfdbcf4701000c1dad85b33b4a0e7ef/index.ts)、[配置](https://github.com/FIND-Lab/AgentWard/blob/46309333bdfdbcf4701000c1dad85b33b4a0e7ef/config.ts)、[会话状态](https://github.com/FIND-Lab/AgentWard/blob/46309333bdfdbcf4701000c1dad85b33b4a0e7ef/core/state.ts)。

架构对照用于说明由宿主 Broker 和 Linux 隔离实施的任务权限边界。具体产品表现需要在统一任务和业务场景下实测检验。

## 已有工作与新价值

[CaMeL](https://github.com/google-research/camel-prompt-injection) 已研究信息来源与允许读者；[Microsoft Agent Framework / FIDES](https://learn.microsoft.com/en-us/agent-framework/agents/security) 已实现会话标签和执行前检查；[bubblewrap](https://github.com/containers/bubblewrap) 提供实际 Linux 隔离。元星木不能把这些原理重新起名就当成发明。

[Hermes iron-proxy 文档](https://github.com/NousResearch/hermes-agent/blob/2237be355906fbe6065ce1815711eee52b2d646e/website/docs/user-guide/egress/iron-proxy.md)已经说明凭证代理的边界：直接 socket 绕过以及向允许域名夹带私密正文，不是仅靠代理替换密钥就能解决。元星木当前用关闭直接出口和任务读取限制处理限定工作环境中的这两个问题，仍需把所有宿主出口纳入同一权限归属。

值得积累的是完整可用的安装与工作过程、跨重启和子任务的一致权限、接入真实业务时的授权方式，以及失败后仍能保留工作记录的处理方式。这些都需要普通用户实际使用和持续复测。

## 对开源与商业化的决定

开源应给出可以安装的程序、自己的模型接入方式、完整的失败记录和升级复测。第一次使用先完成一件小事：选一份报价，让模型列出费用，核对结果，暂时关闭后再继续。开发者仍可使用执行核心、OpenClaw / Hermes 接法和发送演示；已有证据保留，不能让演示替代用户自己的操作。

商业化先验证是否有人愿意反复用它处理自己的资料。进一步的收费方向包括团队资料与权限接入、统一配置和撤销、工作记录查询，以及部署和运行支持。需要这些功能的公司可以成为后续客户，但当前不能把企业功能或市场需求写成已被验证。

对 2–4 人团队，接下来的顺序是：先把安装、自己的模型和资料、关闭后继续这条流程做稳；观察真实用户卡在哪里；再选择一种确有需求的外部服务，做明确授权和本人确认的提交过程。同时测试攻击模型在能力与尝试次数增加时的表现。每一步都记录正常工作的完成情况，不能通过禁止一切动作获得“安全”。
