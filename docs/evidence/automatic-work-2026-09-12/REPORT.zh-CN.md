## 验证了什么

- 获准的消息、文本上传、表单产生本机真实回执，记录授权来源为创建时范围，人工批准时间为空。
- 原 `prepare_action` 继续只生成提案；同一个请求不能改用自动工具升级执行，人工修改过的版本不能复用旧候选检查。
- 检查模型回答 allow 后，宿主仍在开始尝试的同一事务中检查当前资料权限和额度。越权标签、新目标、过期目标绑定、撤权、暂停和不足额度不能产生自动请求。
- 子任务共享原工作额度；收缩后的子任务权限仍生效。两条数据库连接争最后一个额度时只开始一次尝试。
- 接收端已收到请求但断开回复，状态保留为未知。相同目标与完整内容换新请求编号、换子任务或重启，均不会再自动发出，哪怕额度仍有剩余。人工编辑后执行未知的相同内容也纳入检查。已成功确认的操作可以在明确的新请求中再次执行。
- 完整扣留的恶意外部输入不交给 Agent，任务可继续其他获准操作；不清除资料限制、旧暂停、撤权或未处理的人工提案。其他层与记录失败仍保留暂停行为。
- 自动范围只保存在宿主；浏览器提交对刚读取的对象摘要做两次核验。排队期间对象被替换，旧勾选不能授权新地址。

未知结果的重复检查匹配规范化后的精确内容，不能识别任意换词后的语义重复。新内容仍受原目标、权限、防护与累计额度约束。

## 保留的失败与材料

第一轮 Linux 归档验证在 `linux/` 中：311 通过、1 失败。失败发生在外部测试启动脚本未加 `if __name__ == '__main__'`，使 multiprocessing 子进程再次执行启动脚本并错误解析相对路径。补上启动保护后，同一产品归档在 `linux-final/` 中 312 项通过；产品代码没有因该错误改变。

`windows/`、`hermes/` 和 `linux-final/` 各自保存完整日志、跳过原因、运行环境及代码前后摘要。`verification-runner.py` 是修正后的外部启动脚本。使用 `--repo` 指定该提交的源码归档、`--output` 指定新目录、`--commit` 指定完整提交号；官方 Hermes 组件额外提供其已安装的 Python/source，并加 `--hermes`。它不会启动生产 Agent 或调用模型。

本报告依据执行记录，不用“已拦截”的界面文字代替实际副作用检查。原生 Hermes 与 GLM-5.2 的自动流程将单独保留录屏、工具候选和接收端记录。
